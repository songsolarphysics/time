# 数据兼容性

这个文件夹保证：以前任何版本导出的备份，以后的版本都能完整读进来。

## 里面有什么

- `backup-<版本>.json`：同一份样本数据，由各个版本自己导出的完整备份（JSON）。从 2026-10-21a（清新版）开始，样本里还有：待办的类型、属于哪条长期待办、长期待办的手动进度、备注、详情便签，以及自己改过的类型列表；从 2026-10-21b 开始还有：有子待办但手动填进度的长期待办、删掉过的类型、从旧功能转来的待办。样本覆盖所有数据类型：便签（每日、文件夹、项目、星标、公式、表格、链接）、待办（今天、某天、本周、长期，以及放进甘特图的，从 2026-10-20a 开始；重复待办、挂在甘特图任务下的待办、从便签勾选框转来的待办，从 2026-10-20c 开始）、甘特图任务和里程碑（含按待办自动算进度的任务）、推进记录、论文、申请、等回复、文献和 BibTeX、会议、打卡、专注（含绑定了待办和项目的记录）、倒数日、周回顾、链接、记账、看板、数值记录、侧边栏设置、日历订阅设置、便签模板，还有一个“以后版本才有”的集合，用来确认不认识的数据也会原样保留。内容都是虚构的。
- `check.js`：把每份样本导入当前的 `index.html`，再导出，逐条、逐个字段核对，并再导入一次确认结果不变。

## 发布新版本之前

```
npm i playwright && npx playwright install chromium
node compat/check.js
```

（检查脚本会先把备份复制到临时目录再上传：文件夹路径里有中文时，浏览器读不到要上传的文件。）

全部显示“完整”才能发布。只要有一条显示“丢失”或“变化”，说明新版本会弄丢旧数据，先修好。

发布以后：用新版本打开，导入最新的一份 `backup-*.json`，给新功能补几条样本数据，再导出，存成 `backup-<新版本号>.json` 放进来。

## 改数据格式的规矩

1. 只加不改。新功能用新的集合或新的可选字段；已有字段不改名、不改含义、不删。
2. 读旧格式的代码（`normalize` 和各个 `norm*` 函数）永远不删。最早一版的便签是按日期存成一个对象，现在也还能读。
3. 不认识的集合、不认识的设置原样保留，写回时一起带上（`xextra`、`normAny`）。
4. 字段的上限只能放宽，不能收紧（单条便签现在最多 100 万字）。
5. 备份文件里的 `version` 是数据格式版本，`exportedBy` 是导出它的页面版本。

## 2026-10-20c 新加的可选字段

都是可选的；旧版页面读到会忽略（写回时可能丢掉，新版页面会在同一个浏览器里把完整的再存一次，同步时也会把完整的推上去）。

- 待办 `repeat`：重复方式，`day` 每天、`wd` 工作日、`week` 每周、`2week` 隔周、`month` 每月、`year` 每年。做完时生成下一次，规则交给下一次。
- 待办 `orig`：本周待办是“最初计划在哪一周”（那周的周一）；按周、月、年重复的待办是锚点：下一次按它的星期几、几号（每年还有月份）排，而且排在它之后（提前做的这一次，锚点就是原来排的那天）。每月 29–31 号在短的月份落到月底；“每月 31 号”这类的锚点写成一月的那天（一月有 31 天）。
- 待办 `next`：重复待办做完（或这一次单独挪走）后，生成的下一次的 id。
- 待办 `task`：挂在甘特图里哪个任务下面（任务 id）。
- 任务 `auto`：进度按挂在它下面的待办自动算（做完几条 / 一共几条）。
- 专注记录 `todo`、`group`：这段专注是为哪条待办、哪个项目做的。


## 2026-10-21a（清新版）的数据变化

界面改成三部分：便签、待办（短期 / 长期，每条有类型）、甘特图。数据格式只加不改：

- 待办新加的可选字段（旧版页面读到会忽略）：
  - `cat`：类型的 id（默认七种：`main` 主力工作、`collab` 合作论文、`talk` 会议报告、`trip` 出差、`apply` 申请、`social` 社交安排、`misc` 杂事；自己加的类型 id 以 `c` 开头）。没有 `cat` 的显示为“未分类”。
  - `parent`：属于哪条长期待办（那条待办的 id）。旧数据里的 `task`（挂在甘特图任务下）照常读，换算成那个任务转来的长期待办。
  - `prog`：长期待办手动填的进度（0–100）。有子待办时，进度按子待办做完几条自动算。
  - `memo`：备注。
  - `noteId`：详情便签的 id。
- 类型列表存在 `settings` 里，id 是 `cats`：`{id:'cats', list:[{id, name, color}], updated}`。没有这一条时用默认的七种。
- 旧版甘特图里的任务（`tasks`）：原样保留，不改；新版打开时，每个任务转出一条长期待办，id 固定是 `g-<任务 id>`（两台设备各自转出来是同一条，不会重复）。在新版里删掉这条长期待办时，原来的任务也会标成删除，免得以后又转出来。
- 推进记录（`log`）、论文、申请、等回复、文献、会议、打卡、专注、倒数日、周回顾、链接、记账、看板、数值记录、侧边栏设置：新版不再显示，但都原样保留、照常同步、照常导出。
- 本机存储和 Gist 主文件、备份文件里的 `version` 从 3 改成 4（旧版页面读到 4 照常工作）。新版读到 3（旧版页面写的）时，旧版页面看不到也改不了的新字段（类型、属于、进度、备注、详情便签）从本机这份补回来：旧版页面勾掉一条待办，不会把它的类型和备注弄丢。
- 旧版页面后来又改了某个甘特图任务（比 `g-` 那条长期待办新）：新版会把名称、日期、进度跟着更新，类型、备注、子待办保留。旧版页面删掉的任务，转来的长期待办也跟着删（之后在新版里改过的不动）。

## 2026-10-21b 的数据变化

- 待办新加的可选字段 `pman`：长期待办有子待办时，进度也用手动填的 `prog`，不按子待办算（`true`，只有长期待办有）。
- 类型设置 `cats`：列表里每一项可以有 `t`（这一项最后一次加进来、改名、换色的时间）；新加 `gone`：`{类型 id: 删掉的时间}`。两台设备合并时，每个类型取两边里 `t` 较晚的那份；`gone` 的时间比它的 `t` 晚，就不留。顺序按较新的那份。
- 旧功能转成待办：申请材料、会议出差、论文流程、等回复、倒数日、看板里还在进行的条目，可以手动转成待办。转出来的 id 固定是 `m-<集合>-<条目 id>`（会议的摘要、注册截止是 `m-trips-<id>-abs` / `-reg`，挂在会议那条下面），`src` 记着来源 `<集合>:<条目 id>`。原来的条目一字不改。转出来的待办 `updated` 用原来条目的修改时间：两台设备各转一次也只有一条，先转的那台之后改过的不会被后转的盖掉。
- `version` 从 4 改成 5。新字段从哪个版本开始有，记在 `NEW_TODO_F` 里（`cat`、`parent`、`prog`、`memo`、`noteId` 从 4 开始，`pman` 从 5 开始）。读到旧版本页面写的数据时，只把那个版本还不认识的字段从本机这份补回来：4 版页面写回的数据会补 `pman`，但它改过的类型、备注照常生效。
- 删除标记：别的数据删掉 90 天以后，删除标记就不再同步、不再导出；`g-` 和 `m-` 开头的待办（从甘特图任务、旧功能转来的）删掉以后，删除标记一直留着，免得新设备又转一次。
- 本机数据是旧版页面最后写的（本机存储里的 `version` 比当前的小）：记在 `xiangmu-tuijin-oldlocal`（`{v, t}`）。下次和 Gist 同步时，本机较新的待办，旧版页面不认识的字段从 Gist 那份补回来；同步完就清掉这个记号。
